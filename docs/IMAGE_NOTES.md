# 原图与识别文字关联保存

后端0.4.2、插件0.3.0新增本地图片附件能力，保留现有STDIO MCP，不增加远程API或公网服务。

## 日常使用

在电脑或手机远程Codex会话中上传图片后说：

> 提取图片中的文字，无法辨认的地方注明，先给我核对。

确认后说：

> 把这张原图和核对后的文字一起存入知识库。

默认先展示识别稿，等待人工核对、修正或确认，重点检查金额、日期、编号和单位；即使最初说“识别并保存”，也先完成核对。若已提供核对后的最终稿并明确要求保存，则不重复确认。识别稿用summary，保留无法辨认和不确定的内容，不把推断当事实。仅识别或讨论不会触发写入。

保存成功后核对最终文字、images关联，并读取关联原图后再确认图文均已保存。只存入文字或原图读取失败时，应如实报告，不把部分成功当作全部完成。插件0.3.1补充了这一工作流程，后端仍为0.4.2，不需要更换Docker镜像。

助手必须先确认原始附件文件在连接的电脑上可访问。图片理解由当前Codex完成，项目不自动调用OCR或视觉API。图片未传到电脑、只有缩略图或无法访问原文件时，必须明确说明，不能声称原图已保存。远程手机附件传输取决于客户端，本项目的测试不代表手机端上传已经验收。

以后说：

> 查找那张图片里的付款记录，并展示关联原图。

先按已保存的识别文字检索，再用结果中的note_id和images[].image_id调用read_note_image，工具返回原图图片内容。当前是以文字找图，不是以图搜图；图片理解有误时需要修订文字，不能把识别结果当作绝对准确原文。

## 保存链路

1. 助手在宿主机把已获用户授权的原始文件按字节复制到`knowledge_workspace/vault/<空间>/.incoming/`。不修改、压缩、裁剪、重新编码原图，也不擅自删除用户原文件。插件所在项目之外的文件复制可能需要客户端授予相应路径权限。
2. capture_note新增可选`image_paths`，使用vault相对路径，例如`["inbox/.incoming/photo.png"]`。不能传`C:/...`或`/data/vault/...`这类绝对路径，更不能读取vault之外的文件。目标空间仍须有写权限。
3. 支持PNG、JPEG、WebP；最多5张、每张10MiB，按扩展名及基本文件头检查。HEIC、GIF等需另外处理，不能悄悄转换后冒称原图。
4. 保存到`vault/<空间>/.assets/<笔记ID>/<SHA256>.<后缀>`，不重新编码；相同笔记内重复图片按哈希去重。扩展名规范化不会改变文件字节。
5. 识别文字保留在正文前部，正文尾部增加Markdown原图引用。识别稿建议source_type=summary，明确识别不确定处。引用随正文一起进入PostgreSQL和历史版本，不新增数据库表或改变原始图片。
6. 普通失败会清理此次新建的托管图片；提交结果未知时保留用于核对，不宣称文件系统与数据库跨系统原子提交。写入继续使用原有审计和request_id幂等机制。

暂存图片不会自动删除，便于同一request_id重试。成功确认后可手动清理.incoming，不能删除.assets。清理后不应再用已删除的暂存路径重放保存，应读取已有笔记确认结果。

## 查询、权限和版本

- search_notes、read_note、时间线结果增加images列表，含image_id、media_type、relative_path、available和图片引用。
- available只表示文件当前存在；read_note_image会验证文件SHA256和格式后再返回图片。缺失或损坏明确报错，不返回替代图片。
- 图片读取先检查当前笔记的读取权限、活动状态及原文哈希，再核对图片是否关联到该笔记。不能凭哈希读取其他空间或其他笔记的图片。
- 归档、清理索引后普通连接不能读取该笔记的图片；托管原图仍保留，不随归档删除。管理员恢复原笔记后可再次访问。
- 追加、手动编辑后同步和笔记改名均可保留正文中的图片引用；手动删除引用则当前笔记不再关联图片，历史版本仍保留旧引用。
- .incoming、.assets为隐藏子目录，不会被sync当作独立笔记扫描。原文、暂存图和托管图均在被Git及Docker构建忽略的vault内。
- 备份必须同时包含PostgreSQL和整个vault；只备份数据库无法恢复图片。
